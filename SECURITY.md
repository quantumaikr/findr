# Security

findr reads a person's own files. This page says what it does with them, what it does not protect against, and how to report a problem. [한국어 요약](#한국어-요약)은 아래에 있습니다.

## What findr does
- **Everything runs on the PC.** File contents, questions and search history are not sent anywhere. The internet is used to download models and the engine during setup and updates, and for nothing else.
- **Files are only read.** findr never changes, moves or deletes the files it searches.
- **Secret files are not read.** Files such as `.env`, `.netrc`, SSH and PuTTY keys, certificates and key stores (`*.pem`, `*.pfx`, `*.p12`, `*.ppk`, `*.kdbx` and similar) are skipped by name. So are Korean joint certificates (`signCert.der`, `signPri.key`, `kmCert.der`, `kmPri.key`, anything in an `NPKI`, `GPKI` or `EPKI` folder or under a path naming 공동인증서 or 공인인증서), saved-password exports (`passwords*.csv`, `logins.csv`, the CSV files browsers export) and browsers' password stores, and password-manager exports (Bitwarden, 1Password, LastPass, KeePass, Dashlane and others). Their contents are never read; a file indexed before a rule was added loses its stored text on the next run. Folders such as `.ssh`, `.aws`, `.kube` and `.docker` and shell history are never indexed. The rules hold for the names systems give copies (`logins 2.csv`, `Copy of logins.csv`, `passwords.csv.txt`, `비밀번호 - 복사본.csv`, decomposed Korean, trailing spaces and dots such as `.env `), for `.envrc`, `.npmrc`, `.pypirc`, `kubeconfig` and files inside those folders, for names with invisible characters (zero-width spaces and joiners, BOM, word joiner) or other Unicode spaces (U+3000, no-break space), for `id_rsa`, `id_dsa`, `id_ecdsa` and `id_ed25519` with any suffix, for any `.csv`, `.tsv` or `.txt` with a password export's header on one of its first five non-empty lines (English or Korean columns, `pw`/`pwd` included), for password-manager exports recognised by their content under any name (a KeePass XML; JSON or XML records with a password field next to a user name or site field, as Bitwarden, 1Password `.1pif` and Firefox write them), for mail attachments (a name carrying a Windows or POSIX folder is judged by its last part), and for links: a link is judged by where it leads, and a link out of the chosen folders is listed by name only. A mail inside a mail is indexed by name only: an attached mail, a mail whose whole body is `message/rfc822`, and a text attachment that is itself a mail. A file that is one of findr's own data files under another name (a hard link) is not indexed.
- **Where a file came from.** findr reads the download record the operating system keeps for each file (macOS download attributes, the Windows `Zone.Identifier` stream, Linux `user.xdg.*` attributes). Only the site's host name or the app's name goes into the index; the full address and a mail's sender and subject are not kept. Online-only cloud files are not opened. `FINDR_ORIGIN=0` turns this off.
- **Key-like strings are masked.** Text that looks like an API key, token or password setting is replaced before it is stored in the index, and again in everything findr returns: the search page and its API, `read_file`, excerpts. That covers cloud and service tokens (AWS, GitHub, GitLab, Slack tokens and webhooks, Stripe, npm, SendGrid, Google `GOCSPX-` and `ya29.`, Twilio ids and auth tokens next to the word, Azure `AccountKey=`, `SharedAccessSignature=` and `sig=`), Bearer tokens and JWTs, PEM, PGP and PuTTY private keys (cut short, in any letter case, with the header split over two lines, or written out in base64), the password in `scheme://user:password@host` (up to the last `@`, so a password holding `@` or `/` is masked whole), and any value under a label that names a secret, whatever its length: JSON, YAML and INI keys such as `password`, `passwd`, `pwd`, `secret`, `token`, `api_key`, `client_secret`, `DB_PASS`, XML elements and KeePass values, and Korean labels (`비밀번호`, `암호`, `패스워드`, `비번`). A quoted value is masked inside its quotes, an unquoted one to the end of the line (`password: a phrase with spaces`).
- **The search page is local and needs a password.** It listens on `127.0.0.1` only. Repeated wrong passwords are refused for a while. Responses carry a content security policy, forbid framing and are not cached.
- **One data folder.** The index, models, settings, logs and what findr learned from use are in `%LOCALAPPDATA%\findr` (Windows) or `~/.findr` (macOS, Linux). Uninstalling removes it; see the README. findr does not search its own data folder. If a folder inside it is chosen for search, only that folder is searched; the index, models, logs and settings stay out.

## What findr does not do
- **The index is not encrypted.** It holds pieces of document text and is protected only by the file permissions of the user account. Against a lost or stolen PC, use the operating system's disk encryption (BitLocker, FileVault, LUKS).
- **Other programs running as the same user can read the index**, as they can read the files themselves.
- **Installers are not code-signed yet.** Download them only from this repository's releases page.

## AI tools (MCP)
When an AI assistant uses findr through MCP, the file names, locations and excerpts it asks for go to that assistant. If the assistant runs in the cloud, they leave the PC there. Set the assistant to ask before each use of a tool. `read_file` returns only text of files already in the index. No tool names, lists or reads anything in findr's data folder, even if it was indexed, and a path there gets the same answer as a path not in the index (links, letter case, `..`, macOS `/System/Volumes/Data/…` paths, hard-linked folders and Windows forms such as `\\?\`, `\\localhost\C$\`, short names or trailing dots do not get around it: folders are compared by identity, not only by text). The indexer leaves its own data folder out the same way. A file with more than one name (a hard link) that is one of the files in the data folder or a `FINDR_MCP_DENY` folder is answered for as not indexed. Notes and odds in `search_files` are worked out from the files it shows only (the engine's own note and `p_none`, computed over its whole list, are not used), the engine is asked for the same number of results whatever is left out, words without the engine are ranked by each shown file alone, and the characteristic words of `file_relations` are ranked by how rare they are among the files the tools may show. More folders can be kept from AI tools with `FINDR_MCP_DENY` (folders separated by `;`, or `:` outside Windows; `C:\x` stays one folder). Each entry should be an absolute path: a relative entry is ignored with a warning on stderr (the server's working folder is whatever the AI app started it in), a `file:` URL is taken as the path it names, a `%`-encoded entry is denied both as written and decoded, and an entry that does not exist is kept and warned about.

## Known limitations
These are left on purpose or could not be removed cheaply; they are listed so nobody relies on more than findr does.
- **The search engine does not know `FINDR_MCP_DENY`.** It is a setting of the MCP server, so the engine ranks files in those folders (and in chosen folders inside the data folder) along with the rest: its candidate pools and cuts relative to the best score still see them. `search_files` leaves them out of what it shows and computes its note and odds from the shown files, but their presence can still change which other files come back and in what order, and with many hidden matches fewer than `limit` files come back. Without the engine, the word search ranks by each file alone and does not have this effect. To keep a folder out of search altogether, leave it out of the searched folders.
- **Hard links are compared with the data folder and the deny folders only.** A file hard-linked to a secret-named file somewhere else is judged by its own name; its content still goes through the content rules and masking. The folders are listed once per tool call (once per index run for the data folder); past 100,000 (200,000) files every hard-linked file is left out instead. The indexer itself does not know `FINDR_MCP_DENY`: such a file is in the index, and only the MCP tools hide it.
- **Masking is by pattern.** A password in a table of a Word or Excel document, one in a sentence without a label (`my password is …`), or a token of a kind not listed above is not recognised. Credential exports are recognised by header in CSV, TSV and text files and by content in JSON and XML, not inside office documents. Content rules apply once a file's content is read; until then it is listed by name only, as every file is.
- **Word rarity for `file_relations` is sampled.** In a large index the sample is taken at even chunk ids over the whole index, hidden files' ids included, so which shown chunks are sampled can shift slightly when hidden files are added; the counts themselves come from shown files only.

## Reporting a vulnerability
Please do not open a public issue. Use GitHub's **Security → Report a vulnerability** on this repository. We answer within 7 days.

## 한국어 요약
- 모든 처리는 PC 안에서 합니다. 인터넷은 설치·업데이트 때 모델과 엔진을 받는 데만 씁니다.
- 검색 대상 파일은 읽기만 합니다. 비밀 파일(`.env`, SSH 키, 인증서 등)과 공동인증서(NPKI·GPKI·EPKI 폴더, `signCert.der`·`signPri.key` 등), 비밀번호 CSV(`passwords*.csv`, `logins.csv`), 비밀번호 관리 앱의 내보내기 파일은 읽지 않습니다. 사본 이름(`logins 2.csv`, `Copy of logins.csv`, `비밀번호 - 복사본.csv`, `passwords.csv.txt`), 끝에 공백·점이 붙은 이름(`.env `), 보이지 않는 글자(폭 없는 공백 등)나 다른 공백(U+3000)이 든 이름, 뒤에 무엇이 붙은 `id_rsa`·`id_ed25519` 등, `.envrc`·`.npmrc`·`kubeconfig`, 비어 있지 않은 앞 다섯 줄 중 하나가 비밀번호 내보내기 머리글인 모든 `.csv`·`.tsv`·`.txt`(`pw`·`pwd`·비번·암호·아이디·사이트·도메인 등), 이름과 상관없이 내용으로 알아본 비밀번호 관리 앱 내보내기(KeePass XML, 비밀번호 칸과 아이디·사이트 칸이 함께 있는 JSON·XML), 메일 첨부(이름에 붙은 Windows·POSIX 폴더는 떼고 판단), 비밀 파일을 가리키는 링크도 같습니다. 고른 폴더 밖을 가리키는 링크는 이름만 색인합니다. 메일 속 메일(첨부된 메일, 본문 전체가 `message/rfc822`인 메일, 그 자체가 메일인 텍스트 첨부)은 이름만 색인합니다. findr 데이터 폴더의 파일에 하드링크로 붙은 다른 이름도 색인하지 않습니다.
- 키처럼 보이는 문자열(클라우드·서비스 토큰과 Slack 웹훅·npm·SendGrid·Google·Twilio·Azure `AccountKey=`·`sig=`, Bearer·JWT, PEM·PGP·PuTTY 개인 키(끝이 잘려도, 소문자·두 줄로 나뉜 머리줄·base64로 적힌 것도), 주소 속 `user:비밀번호@`(비밀번호에 `@`가 있어도), 그리고 비밀을 뜻하는 이름 뒤의 값은 길이와 상관없이: JSON·YAML·INI의 `password`·`pwd`·`secret`·`token`·`api_key`·`DB_PASS` 등, XML·KeePass 값, `비밀번호:`·`암호 =`·`패스워드`·`비번`)은 저장할 때와 돌려줄 때(검색 화면·API·`read_file`·발췌) 모두 가립니다. 따옴표 안의 값은 따옴표 안을, 따옴표 없는 값은 줄 끝까지 가립니다.
- 파일을 어디서 받았는지(운영체제가 남긴 다운로드 기록)를 읽어, 사이트 이름이나 앱 이름만 색인에 둡니다. 전체 주소나 메일의 보낸 사람·제목은 저장하지 않습니다. `FINDR_ORIGIN=0`으로 끌 수 있습니다.
- 검색 화면은 이 PC(127.0.0.1)에서만 열리고 비밀번호가 필요합니다.
- **색인은 암호화되어 있지 않습니다.** PC 분실에 대비하려면 운영체제의 디스크 암호화(BitLocker, FileVault)를 쓰세요.
- AI 도구(MCP)에 연결하면 찾은 파일의 이름과 내용 일부가 그 AI 도구로 전달됩니다. 클라우드 AI라면 PC 밖으로 나갑니다. findr 데이터 폴더 안의 파일은 AI 도구에 알려 주지 않으며, 더 뺄 폴더는 `FINDR_MCP_DENY`로 정할 수 있습니다. 링크·대소문자·macOS `/System/Volumes/Data/…`·Windows의 `\\?\`·`\\localhost\C$\`·짧은 이름으로 돌아가도 폴더를 그 실체로 비교해 막고, 색인기도 같은 방법으로 자기 데이터 폴더를 뺍니다. 데이터 폴더·`FINDR_MCP_DENY` 폴더의 파일에 하드링크로 붙은 다른 이름도 알려 주지 않습니다. `search_files`의 안내문과 확률은 보여 주는 파일만으로 계산하고(엔진의 안내문·`p_none`은 쓰지 않음), 엔진에는 늘 같은 개수를 물으며, 엔진 없이 찾을 때와 `file_relations`의 특징 낱말 순서도 보여 줄 수 있는 파일만으로 정합니다. `FINDR_MCP_DENY`에는 절대 경로를 적으세요. 상대 경로는 경고(stderr)와 함께 무시하고, `file:` 주소는 그 경로로, `%`로 인코딩된 값은 적힌 그대로와 푼 꼴 모두로 막으며, 없는 폴더는 남겨 두고 경고합니다.
- **알려진 한계**: (1) 검색 엔진은 `FINDR_MCP_DENY`를 모릅니다(MCP 서버의 설정). 그 폴더의 파일은 엔진의 후보·순위 계산에 함께 들어가므로, MCP가 보여 주지 않더라도 다른 파일이 나오는지와 그 순서가 달라질 수 있고, 숨긴 파일이 많이 맞으면 `limit`보다 적게 나옵니다. 엔진 없이 찾을 때는 이 영향이 없습니다. 아예 검색에서 빼려면 검색 폴더에서 빼세요 (2) 하드링크는 데이터 폴더·막은 폴더의 파일과만 비교합니다. 다른 곳의 비밀 이름 파일에 붙은 하드링크는 제 이름으로 판단하고(내용 규칙과 가리기는 그대로), 색인기는 `FINDR_MCP_DENY`를 모르므로 그런 파일은 색인에 있고 MCP만 숨깁니다. 파일이 10만(데이터 폴더는 20만) 개를 넘으면 하드링크 파일을 모두 숨깁니다 (3) 가리기는 꼴로 알아봅니다. Word·Excel 표 속 비밀번호, 이름표 없는 문장 속 비밀번호, 위에 없는 종류의 토큰은 알아보지 못하고, 비밀번호 내보내기는 CSV·TSV·텍스트(머리글)와 JSON·XML(내용)에서만 알아봅니다 (4) `file_relations`의 낱말 드묾은 큰 색인에서 조각 번호로 고르게 뽑은 표본으로 셉니다. 셈은 보여 줄 수 있는 파일만으로 하지만, 숨긴 파일이 생기면 어떤 조각이 뽑히는지는 조금 달라질 수 있습니다.
- 취약점은 공개 이슈 대신 GitHub의 **Security → Report a vulnerability**로 알려 주세요. 7일 안에 답합니다.
