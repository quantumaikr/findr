# Security

findr reads a person's own files. This page says what it does with them, what it does not protect against, and how to report a problem. [한국어 요약](#한국어-요약)은 아래에 있습니다.

## What findr does
- **Everything runs on the PC.** File contents, questions and search history are not sent anywhere. The internet is used to download models and the engine during setup and updates, and for nothing else.
- **Files are only read.** findr never changes, moves or deletes the files it searches.
- **Secret files are not read.** Files such as `.env`, `.netrc`, SSH and PuTTY keys, certificates and key stores (`*.pem`, `*.pfx`, `*.p12`, `*.ppk`, `*.kdbx` and similar) are skipped by name. So are Korean joint certificates (`signCert.der`, `signPri.key`, `kmCert.der`, `kmPri.key`, anything in an `NPKI`, `GPKI` or `EPKI` folder or under a path naming 공동인증서 or 공인인증서), saved-password exports (`passwords*.csv`, `logins.csv`, the CSV files browsers export) and browsers' password stores, and password-manager exports (Bitwarden, 1Password, LastPass, KeePass, Dashlane and others). Their contents are never read; a file indexed before a rule was added loses its stored text on the next run. Folders such as `.ssh`, `.aws`, `.kube` and `.docker` and shell history are never indexed. The rules hold for the names systems give copies (`logins 2.csv`, `Copy of logins.csv`, `passwords.csv.txt`, `비밀번호 - 복사본.csv`, decomposed Korean, trailing spaces and dots such as `.env `), for `.envrc`, `.npmrc`, `.pypirc`, `kubeconfig` and files inside those folders, for names with invisible characters (zero-width spaces and joiners, BOM, word joiner) or other Unicode spaces (U+3000, no-break space), for `id_rsa`, `id_dsa`, `id_ecdsa` and `id_ed25519` with any suffix, for any `.csv`, `.tsv`, `.txt`, `.md` or `.log` with a credential table's header on one of its first 20 non-empty lines (a column naming a password — `password`, `passwd`, `pwd`, `passcode`, `passphrase`, `비밀번호`, `비번`, `암호`, `패스워드` anywhere in its name, or `pw`, `pin`, `pass` as its whole name — next to a column naming an account, person or site — `user`, `login`, `account`, `email`, `mail`, `name`, `site`, `url`, `host`, `domain`, `service`, `id` at its end, `아이디`, `계정`, `이메일`, `사용자`, `사이트`, `주소`, `도메인`, `서비스` anywhere in it; split by `,`, `;`, tab or `|`, so Markdown tables count; an over-long column is left out rather than the whole line), for password-manager exports recognised by their content under any name (a KeePass XML; JSON or XML records with a password field next to a user name or site field, as Bitwarden, 1Password `.1pif` and Firefox write them), for mail attachments (a name carrying a Windows or POSIX folder is judged by its last part), and for links: a link is judged by where it leads, and a link out of the chosen folders is listed by name only. A mail inside a mail is indexed by name only: an attached mail, a mail whose whole body is `message/rfc822`, and a text attachment that is itself a mail (also after blank lines or an mbox `From ` line) or that holds a MIME part header (a multipart `Content-Type`, or a base64 attachment). A file that is one of findr's own data files under another name (a hard link) is not indexed.
- **Where a file came from.** findr reads the download record the operating system keeps for each file (macOS download attributes, the Windows `Zone.Identifier` stream, Linux `user.xdg.*` attributes). Only the site's host name or the app's name goes into the index; the full address and a mail's sender and subject are not kept. Online-only cloud files are not opened. `FINDR_ORIGIN=0` turns this off.
- **Key-like strings are masked.** Text that looks like an API key, token or password setting is replaced before it is stored in the index, and again in everything findr returns: the search page and its API, `read_file`, excerpts. That covers cloud and service tokens (AWS, GitHub, GitLab, Slack tokens and webhooks, Stripe, npm, SendGrid, Google `GOCSPX-` and `ya29.`, Twilio ids and auth tokens next to the word, Azure `AccountKey=`, `SharedAccessSignature=` and `sig=`), Bearer tokens and JWTs, PEM, PGP and PuTTY private keys (cut short, in any letter case, with the header split over two lines, or written out in base64), the password in `scheme://user:password@host` (up to the last `@`, so a password holding `@` or `/` is masked whole), Shopify (`shpat_`, `shpss_`), DigitalOcean (`dop_v1_`) and Slack app and refresh tokens (`xapp-`, `xoxe-`), the password in `scheme://:password@host` with no user name, and any value under a label that names a secret, whatever its length. A label is any setting name (letters, digits, `_`, `.`, `-`) that holds `password`, `passwd`, `pwd`, `secret`, `token`, `apikey`/`api_key`, `accesskey`, `privatekey`, `credential` or `passphrase`, glued to other words or not (`dbPassword`, `accessToken`, `clientSecret`, `PGPASSWORD`, `MYSQL_PWD`, `db.password`, `x-api-key`), or ends in `auth` (`basic_auth`) or `pass` after another word (`DB_PASS`); followed by `:`, `=`, `=>` or `->`. Also `PW:`, `pw=` and `P/W:` as words of their own, Korean labels (`비밀번호`, `암호`, `패스워드`, `비번`), XML elements and KeePass values, `<add key="…Password…" value="…">` and `<entry name="password">…</entry>`, PHP `define('DB_PASSWORD', '…')` and calls like it, `Authorization: Basic …`, `curl -u user:password`, `mysql -p…` and `--password …`. A quoted value is masked inside its quotes, an unquoted one to the end of the line (`password: a phrase with spaces`), and a value left for the next lines to the end of its block (YAML `password:` with the value indented below, `|` and `>` blocks, TOML and Python triple quotes, a `\` continuation). Under a credential table's header (the same rule as for files, anywhere in a text: a CSV pasted into a mail's body, a Markdown table in a note) the password column's cells are masked in every row that follows, up to a blank line. Text in UTF-16 and UTF-32 (with or without a BOM) is decoded before any of these rules run. The words `file_relations` reports are taken from the masked text.
- **The search page is local and needs a password.** It listens on `127.0.0.1` only. Repeated wrong passwords are refused for a while. Responses carry a content security policy, forbid framing and are not cached.
- **One data folder.** The index, models, settings, logs and what findr learned from use are in `%LOCALAPPDATA%\findr` (Windows) or `~/.findr` (macOS, Linux). Uninstalling removes it; see the README. findr does not search its own data folder. If a folder inside it is chosen for search, only that folder is searched; the index, models, logs and settings stay out.

## What findr does not do
- **The index is not encrypted.** It holds pieces of document text and is protected only by the file permissions of the user account. Against a lost or stolen PC, use the operating system's disk encryption (BitLocker, FileVault, LUKS).
- **Other programs running as the same user can read the index**, as they can read the files themselves.
- **Installers are not code-signed yet.** Download them only from this repository's releases page.

## AI tools (MCP)
When an AI assistant uses findr through MCP, the file names, locations and excerpts it asks for go to that assistant. If the assistant runs in the cloud, they leave the PC there. Set the assistant to ask before each use of a tool. `read_file` returns only text of files already in the index. No tool names, lists or reads anything in findr's data folder, even if it was indexed, and a path there gets the same answer as a path not in the index (links, letter case, `..`, macOS `/System/Volumes/Data/…` paths, hard-linked folders and Windows forms such as `\\?\`, `\\localhost\C$\`, short names or trailing dots do not get around it: folders are compared by identity, not only by text). The indexer leaves its own data folder out the same way. A file with more than one name (a hard link) that is one of the files in the data folder or a `FINDR_MCP_DENY` folder is answered for as not indexed. Notes and odds in `search_files` are worked out from the files it shows only (the engine's own note and `p_none`, computed over its whole list, are not used), the engine is asked for the same number of results whatever is left out, words without the engine are ranked by each shown file alone, and the characteristic words of `file_relations` are ranked by how rare they are among the files the tools may show. More folders can be kept from AI tools with `FINDR_MCP_DENY` (folders separated by `;`, or `:` outside Windows; `C:\x` stays one folder). Each entry should be an absolute path: a relative entry is ignored with a warning on stderr (the server's working folder is whatever the AI app started it in), a `file:` URL is taken as the path it names, a `%`-encoded entry is denied both as written and decoded, and an entry that does not exist is kept and warned about.

## Known limitations
These are left on purpose or could not be removed cheaply; they are listed so nobody relies on more than findr does.
- **The search engine does not know `FINDR_MCP_DENY`.** It is a setting of the MCP server, so the engine ranks files in those folders (and in chosen folders inside the data folder) along with the rest: its candidate pools and cuts relative to the best score still see them. `search_files` leaves them out of what it shows and computes its note and odds from the shown files, but their presence can still change which other files come back and in what order, and with many hidden matches fewer than `limit` files come back. Without the engine, the word search ranks by each file alone and does not have this effect. To keep a folder out of search altogether, leave it out of the searched folders.
- **Hard links are compared with the data folder and the deny folders only.** A file hard-linked to a secret-named file somewhere else is judged by its own name; its content still goes through the content rules and masking. The folders are listed once per tool call (once per index run for the data folder); past 100,000 (200,000) files every hard-linked file is left out instead. The indexer itself does not know `FINDR_MCP_DENY`: such a file is in the index, and only the MCP tools hide it.
- **Masking is by pattern.** The rules above are general (any setting name holding a secret word, any table under a credential header) but still patterns: a password in a sentence without a label (`my password is …`, `비번은 …`), a label in another language (`Passwort`) or spelled apart (`pass word`, `p@ssword`), a label and value split over lines in other ways (`PASSWORD` / `=` / value on three lines), a bare value with no label or known prefix (a UUID-shaped API key, a random string), a table whose header is not among its first rows or whose columns are named otherwise, a Word or Excel table whose text does not come out as delimited rows, and tokens of kinds not listed above are not recognised. A credential table more than 20 non-empty lines down a file is masked column by column but does not make the file secret. Text an older findr stored is masked again when returned, and files whose stored text the new rules would read differently are read again once; until that run, a table split across two stored pieces may show rows of its second piece. The rules also mask some ordinary text: values of code settings with such names (`token=None`, `add_to_git_credential=True`), the rest of a line after `password:` in prose, a cell under a column named `PIN`. Content rules apply once a file's content is read; until then it is listed by name only, as every file is.
- **File and folder names are never masked.** A name is how a file is opened, so names and paths are returned as they are, in the search page, its API and every MCP tool. A key pasted into a file name (`AKIA….txt`, `ghp_….md`, `sk-….json`, a JWT) is returned with it. Keep secrets out of file and folder names.
- **Word rarity for `file_relations` is sampled.** In a large index the sample is taken at even chunk ids over the whole index, hidden files' ids included, so which shown chunks are sampled can shift slightly when hidden files are added; the counts themselves come from shown files only.

## Reporting a vulnerability
Please do not open a public issue. Use GitHub's **Security → Report a vulnerability** on this repository. We answer within 7 days.

## 한국어 요약
- 모든 처리는 PC 안에서 합니다. 인터넷은 설치·업데이트 때 모델과 엔진을 받는 데만 씁니다.
- 검색 대상 파일은 읽기만 합니다. 비밀 파일(`.env`, SSH 키, 인증서 등)과 공동인증서(NPKI·GPKI·EPKI 폴더, `signCert.der`·`signPri.key` 등), 비밀번호 CSV(`passwords*.csv`, `logins.csv`), 비밀번호 관리 앱의 내보내기 파일은 읽지 않습니다. 사본 이름(`logins 2.csv`, `Copy of logins.csv`, `비밀번호 - 복사본.csv`, `passwords.csv.txt`), 끝에 공백·점이 붙은 이름(`.env `), 보이지 않는 글자(폭 없는 공백 등)나 다른 공백(U+3000)이 든 이름, 뒤에 무엇이 붙은 `id_rsa`·`id_ed25519` 등, `.envrc`·`.npmrc`·`kubeconfig`, 비어 있지 않은 앞 20줄 중 하나가 비밀번호 표 머리글인 모든 `.csv`·`.tsv`·`.txt`·`.md`·`.log`(비밀번호 열: 이름 어디에든 `password`·`pwd`·`passcode`·비밀번호·비번·암호·패스워드, 또는 이름 전체가 `pw`·`pin`·`pass` / 그 옆의 계정·사람·사이트 열: `user`·`login`·`account`·`email`·`name`·`site`·`url`·`host`·`domain`·`service`, 끝이 `id`, 아이디·계정·이메일·사용자·사이트·주소·도메인·서비스. `,`·`;`·탭·`|`로 나눈 표, Markdown 표 포함. 너무 긴 열은 줄 전체가 아니라 그 열만 뺌), 이름과 상관없이 내용으로 알아본 비밀번호 관리 앱 내보내기(KeePass XML, 비밀번호 칸과 아이디·사이트 칸이 함께 있는 JSON·XML), 메일 첨부(이름에 붙은 Windows·POSIX 폴더는 떼고 판단), 비밀 파일을 가리키는 링크도 같습니다. 고른 폴더 밖을 가리키는 링크는 이름만 색인합니다. 메일 속 메일(첨부된 메일, 본문 전체가 `message/rfc822`인 메일, 그 자체가 메일인 텍스트 첨부 — 앞에 빈 줄이나 mbox `From ` 줄이 있어도 —, MIME 부분 머리글(multipart `Content-Type`, base64 첨부)이 든 텍스트 첨부)은 이름만 색인합니다. findr 데이터 폴더의 파일에 하드링크로 붙은 다른 이름도 색인하지 않습니다.
- 키처럼 보이는 문자열(클라우드·서비스 토큰과 Slack 웹훅·npm·SendGrid·Google·Twilio·Azure `AccountKey=`·`sig=`, Bearer·JWT, PEM·PGP·PuTTY 개인 키(끝이 잘려도, 소문자·두 줄로 나뉜 머리줄·base64로 적힌 것도), 주소 속 `user:비밀번호@`(비밀번호에 `@`가 있어도), Shopify `shpat_`·`shpss_`, DigitalOcean `dop_v1_`, Slack `xapp-`·`xoxe-`, 사용자 이름 없는 `scheme://:비밀번호@`, 그리고 비밀을 뜻하는 이름 뒤의 값은 길이와 상관없이: 이름 어디에든 `password`·`passwd`·`pwd`·`secret`·`token`·`apikey`·`accesskey`·`privatekey`·`credential`이 붙어 있는 설정 이름(`dbPassword`·`accessToken`·`clientSecret`·`PGPASSWORD`·`MYSQL_PWD`·`db.password`·`x-api-key`), `auth`로 끝나는 이름, `DB_PASS`, 낱말로 쓴 `PW:`·`pw=`·`P/W:`, `비밀번호:`·`암호 =`·`패스워드`·`비번`, XML·KeePass 값, `<add key="…Password…" value="…">`, PHP `define('DB_PASSWORD', '…')`, `Authorization: Basic …`, `curl -u 아이디:비밀번호`, `mysql -p…`·`--password …`)은 저장할 때와 돌려줄 때(검색 화면·API·`read_file`·발췌) 모두 가립니다. 따옴표 안의 값은 따옴표 안을, 따옴표 없는 값은 줄 끝까지, 다음 줄로 넘긴 값(YAML 들여쓴 값·`|`·`>` 블록, TOML·Python 세 따옴표, `\` 이어 쓰기)은 그 덩어리 끝까지 가립니다. 글 어디든 비밀번호 표 머리글 아래(메일 본문에 붙여 넣은 CSV, 메모의 Markdown 표)는 비밀번호 열의 칸을 빈 줄까지 모든 행에서 가립니다. UTF-16·UTF-32 글(BOM이 없어도)은 제대로 풀어 읽은 뒤 규칙을 적용하고, `file_relations`의 낱말도 가린 글에서 뽑습니다.
- 파일을 어디서 받았는지(운영체제가 남긴 다운로드 기록)를 읽어, 사이트 이름이나 앱 이름만 색인에 둡니다. 전체 주소나 메일의 보낸 사람·제목은 저장하지 않습니다. `FINDR_ORIGIN=0`으로 끌 수 있습니다.
- 검색 화면은 이 PC(127.0.0.1)에서만 열리고 비밀번호가 필요합니다.
- **색인은 암호화되어 있지 않습니다.** PC 분실에 대비하려면 운영체제의 디스크 암호화(BitLocker, FileVault)를 쓰세요.
- AI 도구(MCP)에 연결하면 찾은 파일의 이름과 내용 일부가 그 AI 도구로 전달됩니다. 클라우드 AI라면 PC 밖으로 나갑니다. findr 데이터 폴더 안의 파일은 AI 도구에 알려 주지 않으며, 더 뺄 폴더는 `FINDR_MCP_DENY`로 정할 수 있습니다. 링크·대소문자·macOS `/System/Volumes/Data/…`·Windows의 `\\?\`·`\\localhost\C$\`·짧은 이름으로 돌아가도 폴더를 그 실체로 비교해 막고, 색인기도 같은 방법으로 자기 데이터 폴더를 뺍니다. 데이터 폴더·`FINDR_MCP_DENY` 폴더의 파일에 하드링크로 붙은 다른 이름도 알려 주지 않습니다. `search_files`의 안내문과 확률은 보여 주는 파일만으로 계산하고(엔진의 안내문·`p_none`은 쓰지 않음), 엔진에는 늘 같은 개수를 물으며, 엔진 없이 찾을 때와 `file_relations`의 특징 낱말 순서도 보여 줄 수 있는 파일만으로 정합니다. `FINDR_MCP_DENY`에는 절대 경로를 적으세요. 상대 경로는 경고(stderr)와 함께 무시하고, `file:` 주소는 그 경로로, `%`로 인코딩된 값은 적힌 그대로와 푼 꼴 모두로 막으며, 없는 폴더는 남겨 두고 경고합니다.
- **알려진 한계**: (1) 검색 엔진은 `FINDR_MCP_DENY`를 모릅니다(MCP 서버의 설정). 그 폴더의 파일은 엔진의 후보·순위 계산에 함께 들어가므로, MCP가 보여 주지 않더라도 다른 파일이 나오는지와 그 순서가 달라질 수 있고, 숨긴 파일이 많이 맞으면 `limit`보다 적게 나옵니다. 엔진 없이 찾을 때는 이 영향이 없습니다. 아예 검색에서 빼려면 검색 폴더에서 빼세요 (2) 하드링크는 데이터 폴더·막은 폴더의 파일과만 비교합니다. 다른 곳의 비밀 이름 파일에 붙은 하드링크는 제 이름으로 판단하고(내용 규칙과 가리기는 그대로), 색인기는 `FINDR_MCP_DENY`를 모르므로 그런 파일은 색인에 있고 MCP만 숨깁니다. 파일이 10만(데이터 폴더는 20만) 개를 넘으면 하드링크 파일을 모두 숨깁니다 (3) 가리기는 꼴로 알아봅니다. 규칙은 일반화했지만(비밀 낱말이 든 모든 설정 이름, 비밀번호 머리글 아래의 모든 표) 여전히 꼴입니다. 이름표 없는 문장 속 비밀번호(`비번은 …`, `my password is …`), 다른 언어(`Passwort`)나 띄우거나 바꿔 쓴 이름표(`pass word`, `p@ssword`), 세 줄로 나뉜 이름표·값, 이름표도 알려진 앞머리도 없는 값(UUID 꼴 API 키 등), 앞쪽에 머리글이 없거나 열 이름이 다른 표, 칸으로 나뉜 줄로 나오지 않는 Word·Excel 표, 위에 없는 종류의 토큰은 알아보지 못합니다. 20줄보다 아래의 비밀번호 표는 열만 가리고 파일을 비밀로 보지는 않습니다. 예전 색인의 글은 돌려줄 때 다시 가리고, 새 규칙으로 달리 읽힐 파일은 한 번 다시 읽습니다. 반대로 보통 글도 조금 가립니다(코드의 `token=None` 같은 값, 글 속 `password:` 뒤 나머지, `PIN` 열의 칸) (5) **파일·폴더 이름은 가리지 않습니다.** 이름으로 파일을 열기 때문에 검색 화면·API·MCP 도구는 이름과 경로를 그대로 돌려줍니다. 파일 이름에 넣은 키(`AKIA….txt`, `ghp_….md`, JWT 등)도 그대로 나가므로 이름에 비밀을 넣지 마세요 (4) `file_relations`의 낱말 드묾은 큰 색인에서 조각 번호로 고르게 뽑은 표본으로 셉니다. 셈은 보여 줄 수 있는 파일만으로 하지만, 숨긴 파일이 생기면 어떤 조각이 뽑히는지는 조금 달라질 수 있습니다.
