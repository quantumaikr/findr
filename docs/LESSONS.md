# 현장에서 배운 것

실제 PC에 findr를 설치해 색인하고 검색하면서 찾은 문제에서 나온 원칙입니다. 처음 기록은 2026-11-08의 Apple M3 Mac, 홈 폴더 전체 약 5만 6천 개 파일입니다.
각 원칙은 한 줄 규칙, 실제로 겪은 일(이슈·PR 번호), 지키는지 확인하는 방법 순서로 적었습니다. PR을 올릴 때의 점검표는 [.github/pull_request_template.md](../.github/pull_request_template.md)에 있습니다.

## 1. 장치는 셋이다: NVIDIA, Apple GPU, CPU
**규칙:** 장치를 고르는 코드는 `cuda` / `mps` / `cpu`를 모두 다룬다. `torch.cuda.is_available()` 하나로 GPU 여부를 판단하지 않는다.
**겪은 일:** 의미 모델(#1), 재순위(#7), 글자 인식(#8)이 모두 Apple GPU를 빠뜨렸다. Mac에서 글자 인식은 CPU로 돌아 페이지당 23초가 걸렸다.
**확인:** `pick_device()`를 거치는지 본다. macOS CI에서 시험한다.

## 2. 실패와 '비어 있음'을 구분한다
**규칙:** 읽기에 실패한 결과를 '내용 없음'처럼 저장하지 않는다. 실패는 다시 시도할 조건과 함께 기록한다.
**겪은 일:**
- LibreOffice가 없을 때 빈 변환 결과가 캐시에 남았다. 나중에 LibreOffice를 설치해도 그 파일은 영영 다시 읽히지 않았다(#29, #34).
- 반대로 변환 실패를 기록하지 않아, 같은 파일에 매번 최대 120초를 썼다(#34).
**확인:** `.ok`(정말 비어 있음)와 `.fail`(이 LibreOffice로는 실패)처럼 상태를 나눠 기록한다. 실패에서 회복하는 경로를 시험한다.

## 3. 새 읽기 기능은 기존 색인에도 닿아야 한다
**규칙:** 읽을 수 있는 형식이 늘면 `READERS` 버전을 올리고, 그 형식의 빈 파일을 다시 읽게 한다.
**겪은 일:** 크기, 날짜, 분류가 그대로인 파일은 다시 읽지 않는다. 그래서 배포용 HWP와 옛 엑셀 읽기를 추가해도(#28, #29) 이미 색인된 PC에는 반영되지 않았다(#34).
**확인:** `REREAD_EXT`에 형식을 추가했는지 본다. "한 번만 다시 읽음" 시험을 둔다.

## 4. 멈춘 것처럼 보이면 고장이다
**규칙:** 오래 걸리는 단계는 진행 상황을 보여 주고, 중간 결과를 자주 저장한다.
**겪은 일:**
- PC 전체 색인이 폴더 하나를 마칠 때까지 아무것도 출력하지 않았다(#6).
- 글자 인식은 50개마다만 저장해서 30분 동안 진행률이 0으로 보였고, 중간에 멈추면 결과를 모두 잃었다(#11).
- 색인을 멈춘 뒤에도 "색인 진행 중" 띠가 남았다(#18).
**확인:** 파일 단위로 커밋하는지, `progress.json`이 갱신되는지, 프로세스가 사라지면 표시도 사라지는지 본다.

## 5. 엔진을 바꾸기 전에 일을 줄인다. 다만 운영체제에 있는 것은 먼저 쓴다
**규칙:** 속도 문제는 먼저 할 일을 줄여서 푼다(같은 파일은 한 번만, 앞부분 먼저, 순서 조정). 다음으로 운영체제 기본 기능을 쓴다.
**겪은 일:**
- 사본을 한 번만 읽고 첫 색인은 앞 3장만 읽자 93초가 9초, 157초가 57초가 됐다(#25).
- macOS Vision은 EasyOCR(CPU)보다 37배 빠르고 한국어도 더 정확했다(#15).
- 여러 장 동시 처리, 그림 크기 줄이기는 측정해 보니 효과가 없었다.
**확인:** 바꾸기 전과 후를 같은 파일로 재고, 그 수치를 PR에 적는다.

## 6. 순위 규칙은 함께 시험한다
**규칙:** 검색 순위를 바꾸는 변경은 실제 질문 묶음으로 전후의 1위를 비교한다. 규칙 하나만 보는 단위 시험으로는 부족하다.
**겪은 일:**
- 판(버전) 규칙이 고른 결과를 뒤이은 '문구 일치' 단계가 다시 뒤집었다(#18).
- 낱말 확장 `생성 → gen generate`가 이름 규칙에서 두 낱말로 세어져, 생성 이미지 수십 개가 정답을 후보 밖으로 밀어냈다(#32).
**확인:** 질문 묶음을 돌려 1위가 바뀐 질문만 따로 설명한다.

## 7. 한글 이름은 NFC로 비교한다
**규칙:** 파일 이름과 경로는 NFC로 맞춘 뒤 비교한다. macOS는 NFD로 저장한다.
**겪은 일:** 이름 검색이 빠졌고(#12), 판 규칙이 문서 계열을 찾지 못했다(#18).
**확인:** SQL에서는 `nfc()`, 파이썬에서는 `unicodedata.normalize("NFC", …)`를 쓴다. NFD 이름으로 시험한다.

## 8. 라이브러리보다 공식 명세를 먼저 본다
**규칙:** 형식을 읽는 문제는 공개 명세부터 확인한다. 명세가 요구하는 출처 표기를 지킨다.
**겪은 일:** HWP 도구 5개를 비교해 보니 일반 문서는 모두 잘 읽었고, 빈 곳은 배포용 문서뿐이었다. 그 부분은 한컴 공개 명세로 순수 파이썬 몇십 줄이면 풀렸다(#28). 새 의존성이나 Rust는 필요 없었다.
**확인:** 명세 출처와 표기 문구를 소스와 README에 적는다.

## 9. 실제 PC의 이름은 공개 저장소에 쓰지 않는다
**규칙:** 실제 PC에서 찾은 문제라도 파일 이름, 회사 이름, 사람 이름은 이슈·PR·커밋·코드·시험에 그대로 쓰지 않는다. 일반적인 이름으로 바꿔 쓴다.
**겪은 일:** 측정 예시에 실제 문서 이름이 들어갔다가 나중에 바꿨다(#33). 저장소 이력과 본문 수정 기록에는 그대로 남는다.
**확인:** 올리기 전에 본문과 diff에서 실제 이름을 검색한다.

## 10. 돌고 있는 프로그램의 폴더에서 git 작업을 하지 않는다
**규칙:** 색인이나 검색 서버가 쓰는 작업 폴더에서는 브랜치 전환, rebase, pull을 하지 않는다. 별도 `git worktree`를 쓴다.
**겪은 일:** rebase 도중 충돌 표시가 남은 `index.py`를 색인이 불러와, 남은 폴더 넷이 모두 실패했다.
**확인:** 개발은 worktree에서 하고, 실행 중인 폴더는 그 일이 끝난 뒤에 갱신한다.

## 11. 머지 전에 작성자가 아닌 눈으로 본다
**규칙:** 작성자의 시험은 작성자의 가정을 따른다. 머지 전에 맥락을 모르는 사람이나 검토 도구가 한 번 본다.
**겪은 일:** 머지된 뒤 받은 독립 검토에서 두 문제가 나왔다(#34). 하나는 RTF가 크기의 제곱으로 느려지는 문제(1.2MB에 약 110초), 다른 하나는 새 읽기 기능이 기존 색인에 닿지 않는 문제였다. 둘 다 작성자의 시험은 통과했다.
**확인:** PR 템플릿의 검토 항목을 채운 뒤 머지한다.

## 12. 업데이트 경로도 설치 경로다
**규칙:** 의존성을 추가하면 이미 설치된 PC가 그것을 받는 경로까지 확인한다.
**겪은 일:** `git pull`만으로는 새 패키지가 설치되지 않아 기능이 조용히 꺼졌다(#31).
**확인:** `findr doctor`가 빠진 의존성을 알려 주는지 본다.
